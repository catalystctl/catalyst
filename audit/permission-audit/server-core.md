# Permission Audit — server-core scope (servers.ts, core.ts, stats.ts, variables.ts, bulk-servers.ts)

Auditor: `audit-server-core` · Repo: `/home/karutoil/catalyst` · All paths relative to `catalyst-backend/`.
Contract audited against: `admin.read` = read everything (every server + every read-only endpoint); `admin.write` = read+write everything; `*` = superadmin; every other permission = one narrowly-scoped capability.

## 1. Executive summary

- **`admin.read` is broken on the two list/status endpoints**: `GET /api/servers` (core.ts:1443) and `POST /api/servers/bulk/status` (bulk-servers.ts:666-667) admit only `admin.write`/`*` to the all-servers path — an `admin.read`-only user sees just their own/assigned servers (A-READ-GAP ×2). Per-server reads (detail, stats, activity, variables) correctly honor `admin.read`.
- **Server creation is reachable with no permission at all**: a bare node assignment (not a permission) authorizes `POST /api/servers` (core.ts:342) — contradicting the "node assignment alone is NOT enough" contract enforced everywhere else.
- **4 routes bypass the API-key scope** (`enforceKeyScope`) on their owner path: `DELETE /:serverId`, `PATCH /:serverId/variables`, `POST /:serverId/storage/resize` (owner bypass) and partially `POST /` (node-assignment path via the owner's key) — a zero-scope API key of the owner can delete servers, edit startup environment, and resize disk.
- **Storage resize accepts `file.write`** as its subuser grant (core.ts:2300) — wrong family; resize is a resource-setting change, not a file-manager action.
- **`server.transfer` has split personality**: it gates node-transfer and cross-node clone but is ignored by transfer-ownership (admin-ops.ts:756-759, owner/admin.write only) even though the owner "full" preset ships it (_helpers.ts:61).
- **Bulk suspend/unsuspend/delete** gates are correct and match the single-server routes (`server.suspend`/`server.delete` + `admin.write`/`*`), but the per-server `hasServerAccess` layer (bulk-servers.ts:46-91) is provably dead code with comments contradicting the code.

### Why the bulk per-server layer is dead code (bulk-servers.ts:46-91)

`ensureBulkPermission` (line 29-40) admits only users holding `*`, `admin.write`, or the exact required perm (e.g. `server.suspend`) in `request.user.permissions`. `hasServerAccess` (line 46-91) reads the **same array** and returns `true` at line 56 (`*`/`admin.write`) or line 61-63 (the required perm) for every such user — the ServerAccess query (line 66), server lookup (line 79) and owner check (line 86-88) are unreachable. The comment at line 84-85 ("Node assignment alone must not grant…") and at line 149-151 ("ownership alone does not suspend") describe checks the code never gets to run; conversely the owner branch at line 86-88 *does* return true for owners, contradicting the comment — it just can't matter because owners fail the global gate first.

### API-key scope context

For API keys, `request.user.permissions` is the **key's** permission set (server.ts:442-511, key perms at :494, `apiKeyId` attached at :515). Routes using `checkPerm`/`checkIsAdmin`/raw `perms.includes` therefore enforce key scope — but routes whose owner branch skips those helpers (DELETE, variables PATCH, storage resize, transfer-ownership; reads without any check) never consult the key's permissions. `ensureServerAccess` exists precisely to fix this via `enforceKeyScope` (_helpers.ts:553-556); the four write routes above bypass it.

## 3. Vocabulary findings

### 3.1 Permission strings used in scope but missing from the catalog

None — every string enforced in scope (`server.create/read/update/delete/suspend/transfer`, `file.write`, `node.update`, `user.create`, `admin.read/write`) exists in `lib/permissions-catalog.ts` `PERMISSION_CATEGORIES` (:18-169). **However**, `lib/permissions.ts` carries a second, stale `PERMISSION_CATEGORIES` (:432-546) missing `server.update`, `server.install`, `server.reinstall`, `server.rebuild` and `backup.download`. It is only consumed by `src/__tests__/rbac.test.ts:494,512`, but it is a drift trap: two "the catalog" exports with different content. Delete the stale copy or make it re-export the canonical one.

### 3.2 Catalog perms never enforced in scope (or enforced only partially)

- `server.transfer` — in catalog (:40) and in `ALL_SERVER_PERMISSIONS` (:241) and the owner-full preset (_helpers.ts:61). Enforced for **node transfer** (admin-ops.ts:389-406, incl. ServerAccess rows) and **cross-node clone** (core.ts:114 — global check only), but **not** for ownership transfer (admin-ops.ts:756-759). One permission currently means "move between nodes" everywhere except the one place its label ("Transfer ownership") points. Split or align (see 3.4).
- `server.install` / `server.reinstall` / `server.rebuild` / `server.schedule` — not enforced in *scope files* (they live in power.ts/tasks routes; listed here only for the completeness of the scoped catalog-vs-code diff).
- `apikey.manage` — not enforced in scope (admin routes own it).
- `server.suspend` — enforced (bulk + suspend family) but is also the gate for **archive** and **restore-from-archive** (admin-ops.ts:837, 907) — a third capability family riding one permission.

### 3.3 Over-broad / mis-scoped permission usage

- **`server.update` is a mega-permission**: name/description (cosmetic), `environment` + `startupCommand` (directly shape container execution), resource allocations (memory/CPU/disk), network config (ports/IP/allocation), restart policy (admin-ops.ts:79-86), crash-count reset (admin-ops.ts:124-131), startup variables (variables.ts:86-112), storage resize. A subuser granted it "to rename the server" can rewrite the startup command. The code itself gestures at this (core.ts:1864-1866 comment) but implements no split — the sensitive-field re-check (core.ts:1867-1893) is unreachable dead code that grants exactly the same `server.update`.
- **`file.write` authorizes storage resize** (core.ts:2300) — wrong resource family (file manager vs disk quota).
- **`user.create` doubles as "create a server for another user"** (core.ts:349, core.ts:113 `canSetOwner`) — a user-management permission reused as a server-provisioning capability. Anyone who can mint users can also deploy servers *as* them, on any node they can reach.
- **`admin.write` fallback where a targeted perm exists**: transfer-ownership (admin-ops.ts:756-759) is the in-family example — `server.transfer` exists and is even preloaded into owner grants, yet the route only accepts owner/admin.write.

### 3.4 Proposed new targeted permissions

| New permission | Exact capability | Endpoints that would use it |
|---|---|---|
| `server.storage.resize` (or fold strictly into `server.update`) | Change a server's disk allocation (grow online / shrink stopped) | `POST /:serverId/storage/resize` (core.ts:2248) — replaces the current `server.update`+`file.write` mix |
| `server.startup.update` (recommended) or keep `server.update` for env only | Edit `environment`, `startupCommand`, startup variables — fields that shape how the container executes | `PUT /:serverId` (env/startup branch), `PATCH /:serverId/variables` |
| `server.resources.update` | Change memory/CPU/disk allocations, ports, IPs, allocations | `PUT /:serverId` (resource branch), `POST /:serverId/storage/resize` |
| `server.transfer_ownership` (or make existing `server.transfer` cover it) | Hand a server to a different owner (grants the new owner the full preset) | `POST /:serverId/transfer-ownership` (admin-ops.ts:734) |
| `server.kill` — *decision needed* | Force-kill (SIGKILL) a running container | `POST /:serverId/kill` currently uses `server.stop` (power.ts:1048). Defensible as one "stop" family; split only if the owner wants force-stop separable. |
| `server.unsuspend` — *decision needed* | Lift a suspension | bulk/power unsuspend currently ride `server.suspend`. Fine as one suspension capability; noted for completeness. |
| Clone: keep `server.create` + source read grade | Clone = create + read-source; no new perm needed, but the source check must become read-grade (see endpoint table) | clone preflight/submit/retry |

Install/reinstall/rebuild separation is **already correct**: `server.install` (power.ts:193), `server.reinstall` (:290), `server.rebuild` (:555) are distinct catalog perms enforced distinctly; cancel-install takes install-or-reinstall (:387). EULA consent rides `server.start` (power.ts:483) — acceptable as part of the install/start lifecycle, worth a label note only.

## 4. Fix list (priority order)

1. **`admin.read` on the list endpoints** — core.ts:1443 (+ fast-path cache key) and core.ts:1640: treat `admin.read` as list-everything (read-subset effectivePermissions, cf. _helpers.ts:1421-1425); bulk-servers.ts:666-667: add `admin.read` to the `isAdmin` check of `/bulk/status`. *Highest impact — this is the primary admin.read contract violation.*
2. **Close the owner-path API-key scope bypass** — add `enforceKeyScope` (or route through `ensureServerAccess`) in: core.ts:2396 DELETE (owner branch :2423), core.ts:2248 storage/resize (:2273), variables.ts:63 PATCH (:86), admin-ops.ts:734 transfer-ownership (:756). Pattern to copy: _helpers.ts:553-556.
3. **Decide the node-assignment create policy** — core.ts:342: drop `hasNodeAccessResult` as an alternative to `server.create` (or require `node.update` pairing). The error message shows this is intentional today; it contradicts the stated contract and the everywhere-else "node assignment alone is NOT enough" rule.
4. **Resize permission family** — core.ts:2300: remove `file.write`; require `server.update` (or the proposed `server.storage.resize`) for subusers; add key-scope to the owner path (covered by 2).
5. **Transfer vocabulary** — admin-ops.ts:756-759: accept `server.transfer` for ownership transfer (ServerAccess row / global role / scoped grant), or remove `server.transfer` from `OWNER_SERVER_PERMISSIONS`/full preset (_helpers.ts:61) and rename the catalog label to "Transfer between nodes" (permissions-catalog.ts:40) to stop advertising a no-op grant.
6. **Clone source read-grade + clone-target check** — core.ts:908/1014/1322: require `server.read`-grade access on the clone source (pass `requiredPermission` into the decision instead of any-row `canAccessServer`); core.ts:1336: add an access check on the clone target for the retry route.
7. **Bulk dead code + comments** — bulk-servers.ts:46-91: delete `hasServerAccess` (or make it meaningful), fix the comments at :84-85 and :149-151 that contradict the code; reconcile owner semantics between single DELETE (owner allowed, core.ts:2423) and bulk DELETE (global `server.delete` required, bulk-servers.ts:457).
8. **Stale duplicate catalog** — lib/permissions.ts:432-546: remove `PERMISSION_CATEGORIES` (test-only consumer, `src/__tests__/rbac.test.ts:494`) or re-export from `lib/permissions-catalog.ts`; it is missing `server.update/install/reinstall/rebuild` and `backup.download`.
9. **(Vocabulary, larger change)** Split `server.update` per §3.4 (`server.startup.update` / `server.resources.update`) and delete the unreachable sensitive-field block at core.ts:1867-1893 once real gates exist. Decide `server.kill` / suspend-unsuspend / archive-restore splits.
