# Permission Audit — Plugin System + MCP Surface

Scope: `catalyst-backend/src/routes/plugins.ts`, `src/plugins/context.ts`, `src/plugins/safety.ts`, `src/plugins/route-table.ts` (+ `loader.ts` mounting, `websocket/gateway.ts` plugin dispatch, `__tests__/route-auth-modes.test.ts`), `src/routes/mcp.ts` (+ `src/mcp/tools.ts`, `src/mcp/protocol.ts`), `packages/plugin-sdk/src/routes.ts`. All claims cite file:line against current code. Companion to `audit/permission-audit/server-files.md` (cross-referenced as SF).

## 1. Executive Summary

Panel plugin-management routes are the cleanest surface audited so far: every write (install/uninstall/enable/reload/permissions/config/marketplace-source writes) requires `admin.write` via `ensureAdmin` (plugins.ts:40-59), and no write route accepts `admin.read`. The two real problems are elsewhere. First, **four plugin read routes have no permission check at all** (plugin list/detail/frontend-manifest/assets — auth-only), exposing the full plugin inventory, declared/granted permissions, and phone-home licensing destinations to every authenticated user and to *any* API key via the MCP `list_panel_plugins` tool. Second, the **plugin-side caller gate `context.requirePermission` uses raw `includes` with only `*` special-cased** (context.ts:1178-1189), so `admin.write`/`admin.read` callers fail concrete-permission checks — the inverse of the panel contract — while plugin routes that *don't* opt in are open to all authenticated users. The consent/safety model itself (safety.ts) is sound: flat subset semantics with `*` only, no admin implications smuggled in; re-acceptance triggers on version/permission/disclaimer change. Two phantom capability tokens exist (`admin.read`/`admin.write` as *plugin* permissions are never enforced anywhere, and `user.write` can never write any field). MCP adds no new authorization path by design (tools re-inject the caller's own key) — it is a correct transport that *inherits and amplifies* every upstream route gap documented in SF.

## 3. Plugin capability-model + escalation findings

- **E1 — delegated caller authorization is the architecture's soft spot.** The host enforces *identity* on plugin routes/WS (authenticate, gateway.ts:3540-3542) and *capabilities* on what plugin code can do (scoped DB, auth bridge, RPC — all live-gated), but **who may call a plugin route is entirely the plugin's decision** (context.ts:786-806; route-table.ts:172-176). A plugin that forgets `requirePermission` exposes its (potentially DB-backed, `server.read`-capable) endpoint to every authenticated user. The two opt-in gates that exist (`requirePermission`/`hasPermission`, context.ts:1161-1189) then *deny legitimate admins* because they lack `hasGrant`'s admin implications — the worst of both directions (default-open, admin-blocking opt-in). This is the single most consequential plugin-surface finding.
- **E2 — critical-risk capabilities are consent-gated but unlimited in blast radius once granted.** `auth.sessions` mints a session for any userId and sets the cookie (context.ts:1270-1288); `roles.assign` grants any role to any user (context.ts:717-749). Both are correctly labeled critical in the consent dialog (safety.ts:102-119), audited, and live-revocable — the model is honest, but these two tokens are each equivalent to full panel takeover; consider a second confirmation (re-type/2FA) when granting them, not just the standard disclaimer.
- **E3 — MCP amplification.** The MCP layer is a faithful, correctly-scoped proxy (tools.ts:4-14, mcp.ts:132) — its security is exactly the security of the underlying routes. Every gap fixed in SF F1-F6 also closes here; conversely, until then, any API key (the MCP surface requires a key, mcp.ts:82) can reach the backup key-scope bypass, the database read gap, and the auth-only plugin inventory through tools. No MCP-layer defect; inheritance must be tracked to closure.
- **E4 — open plugin permission vocabulary.** Plugins may declare arbitrary tokens (PERMISSION_TOKEN_RE, safety.ts:122) which the consent dialog shows as "Custom capability" (safety.ts:201-209). Custom tokens are documentation-only at runtime; tokens colliding with panel names (`server.read`, `user.read`) map to real scoped-DB powers (context.ts:586-593). Acceptable, but reviewers should know only the twelve builtin tokens have runtime meaning.
- **E5 — un-gated WS broadcast** (context.ts:856-863): any enabled plugin can push arbitrary messages to all authenticated clients without any capability declaration; combined with E1 this is the panel-internal phishing/injection channel.
- **E6 — positive findings worth recording:** `routes.public` is enforced *twice* (registration-time downgrade + live per-request re-check, route-table.ts:157-162, with regression test 87-111); plugin middlewares cannot intercept host routes (loader.ts:527-552); backend entry path traversal is jailed (loader.ts:482-489); grants must be ⊆ declared (plugins.ts:899-909) and effective grants live-re-read on every capability check (context.ts:129-142); plugin enablement consent is computed server-side from DB rows, not client claims (plugins.ts:746-789); secret config values are redacted to non-admins with fail-closed unknown-key handling (plugins.ts:88-123).

## 4. Vocabulary findings + proposed targeted permissions

- **V1 — two permission vocabularies exist and must not be conflated.** Panel roles use PERMISSION_CATEGORIES (permissions-catalog.ts:18-169) with `admin.read`/`admin.write` implications (permissions.ts:143-149). Plugin grants use PERMISSION_INFO (safety.ts:53-120) with **flat semantics — `*` only, no implications** (isSubsetOf, safety.ts:148-152). This is correct as designed; the bug is that the *caller-side* helpers in context.ts borrowed the flat semantics (E1/A-READ-GAP row) where panel semantics belong.
- **V2 — plugin-scope `admin.read` / `admin.write` are phantom (D-CATALOG).** Nothing consumes them (context.ts:591-592 maps to no tables; registerRoute never checks). Either give them meaning — e.g. a plugin declaring `admin.write` may register routes that call admin-level upstream APIs, enforced by requiring the declaration and validating it — or delete both tokens and correct the consent copy (safety.ts:81-90), which currently tells reviewers a capability exists that does not.
- **V3 — plugin-scope `user.write` is dead (D-CATALOG).** The whitelist is empty by design (context.ts:98-100: role assignment deliberately blocked), making the consent label "Modify users" (safety.ts:75-80) misleading. Remove the token, or implement a narrow whitelist (e.g. `name`, `image`) so the label is truthful.
- **V4 — propose `ws.broadcast` (plugin capability, high risk):** gates `sendWebSocketMessage('*')` (context.ts:856-863). Capability: push messages to every authenticated panel client. Without it, plugins could only target explicit client ids.
- **V5 — propose `plugin.read` (panel permission, admin-level, NOT server-scoped):** gates the sensitive half of GET /api/plugins, /:name, /:name/frontend-manifest (declared/granted permissions, consent state, licensing destinations, capability inventories). `admin.read` satisfies it via hasGrant; non-admins keep only the minimal fields their UI needs (name, displayName, status). Removes the §2.1 C-NO-CHECKs and the any-key MCP read path. The marketplace reads already use exactly this shape (`ensureAdmin('admin.read')`, plugins.ts:246,274) — the inventory reads are the inconsistent outliers.
- **V6 — SDK `RouteDefinition` auth surface:** no bypass exists today (routes.ts:5-10). Recommend adding an optional explicit `auth?: 'required' | 'optional' | 'public'` field (still grant-gated by context.ts:768-779) so intent is visible in the plugin source rather than implicit.

## 5. Fix list (priority order)

1. **F1 — context.ts:1161-1189: make `requirePermission`/`hasPermission` honor panel semantics.** Replace the raw `includes('*')`/`includes(p)` with `hasGrant(perms, p)` (permissions.ts:143-149) so `admin.write` satisfies any concrete permission and `admin.read` satisfies read-classified ones. Closes the A-READ-GAP where admins are locked out of plugin routes that gate on concrete perms.
2. **F2 — plugins.ts:613-720, 1017-1062: gate plugin inventory reads.** Apply `isAdminCaller(request, 'admin.read')` (already implemented at plugins.ts:66-76) beyond config redaction: return declared/granted permissions, consent state, licensing, capability inventories and configSchema only to admins; keep a minimal public projection (name/displayName/status/entry) for non-admin UI. Fixes 4 C-NO-CHECK rows + the any-API-key path via MCP `list_panel_plugins`/`get_panel_plugin`.
3. **F3 — safety.ts:75-90 + context.ts:591-592: resolve the phantom tokens.** Enforce or remove plugin-scope `admin.read`/`admin.write` and dead `user.write`; update PERMISSION_INFO copy so consent dialogs never claim a capability that does not exist.
4. **F4 — document (or enforce) the delegated-authorization contract.** In the plugin docs/SDK types, state explicitly that the host authenticates identity only on plugin routes and WS handlers, and that plugins MUST call `requirePermission` (fixed per F1) for anything sensitive. Optionally let RouteDefinition declare a required panel permission the host enforces at the dispatcher.
5. **F5 — context.ts:856-863: gate the WS broadcast.** Require a new `ws.broadcast` capability (or remove the `'*'` target) so arbitrary all-client pushes are a declared, consent-visible power.
6. **F6 — plugins.ts:557-607: restrict `/plugins-assets` `.map` files** (sourcemaps can embed original source) to `admin.read` callers, or drop `.map` from ASSET_EXTENSIONS; document the auth-only stance for the remaining asset types if intentional.
7. **F7 — track MCP gap inheritance to closure.** No MCP-layer change; the transport is sound (confirm-gate protocol.ts:151-155, key budget 160-164, API-key-only auth mcp.ts:82-96). Closing SF F1-F6 (backups key-scope, database read gap, database-hosts, SFTP token listing) automatically closes the same tools here — add a note to the MCP docs stating tool security = upstream route security.
