# Permission Audit — Server Files, File Tunnel, Backups, Databases, SFTP

Scope: `catalyst-backend/src/routes/servers/files.ts`, `routes/file-tunnel.ts`, `routes/backups.ts`, `routes/servers/databases.ts`, SFTP token endpoints in `src/server.ts`, plus helpers `_helpers.ts`, `lib/server-access.ts`, `lib/permissions.ts`, `lib/permissions-catalog.ts`, `services/sftp-token-manager.ts`, `catalyst-agent/src/sftp_server.rs`. All file:line references verified against current code.

## 1. Executive Summary

The per-server file routes are clean: every endpoint gates through `ensureServerAccess` with a concrete `file.read`/`file.write`/`console.read` permission, which routes through `decideServerAccess` (admin.read reaches reads, admin.write reaches writes, API-key scope is enforced). Five real problems exist elsewhere: (1) **backups.ts and all SFTP panel endpoints never enforce API-key scope** — they resolve the user's live DB role perms and ignore the key's own permission list, so a narrowly-scoped key of an owner/admin can delete backups or mint an SFTP token that validates to `["*"]` full file R/W; (2) **`admin.read` cannot list a server's databases** because `ensureDatabasePermission` hand-rolls its check without the `admin_read` branch; (3) **`admin.read` cannot list SFTP tokens** because that decision omits `requiredPermission`; (4) the SFTP validate-token permission derivation **returns `[]` for server owners and admin.read users** (owners' SFTP is functionally broken); (5) SFTP token minting is gated by `server.read` (too broad) while a targeted `file.sftp` permission exists only as a phantom comment. The file-tunnel agent endpoints are correctly node-bound and carry no user-path inputs.

### 2.3 backups.ts (prefix /api/servers; helper `ensureBackupAccess` backups.ts:43-96)

The helper checks: owner (66-68) → ServerAccess row containing the permission (69-75) → `hasGrant(rolePerms, permission)` on server-scoped role resolution (80-83, so `admin.read` reaches `backup.read`/`backup.download` and `admin.write` reaches all) → node-assignment **plus** `node.update` (88-91). Suspension enforced (57-65). The one structural defect: **no `enforceKeyScope`** — the helper never receives `request.user`, so on API-key requests the key's scoped permission list (set at server.ts:494,516) is ignored and the user's live DB perms decide alone.

## 3. Vocabulary Findings

- **K1 (systemic, highest impact): API-key scope is enforced inconsistently.** `enforceKeyScope` (_helpers.ts:487-493) is applied by `ensureServerAccess` (files.ts routes ✓, databases.ts routes ✓ via the `actor` argument) but never by `ensureBackupAccess` (backups.ts:43-96 — no actor parameter at all) nor by any SFTP panel endpoint (server.ts:1511-1872). Since API-key auth sets `request.user.permissions` to the key's scope (server.ts:494,516) while these routes re-resolve the user's live role perms from the DB, a key scoped to `[server.read]` acts with the user's full power on backup create/restore/delete/download and SFTP mint/rotate. This is exactly the "broader than intended" write path B-WRITE-LEAK describes.
- **A-READ-GAP pattern: two hand-rolled checkers diverge from `decideServerAccess`.** `ensureDatabasePermission` (_helpers.ts:1446-1515) and the `GET /api/sftp/tokens` decision (server.ts:1744-1749) both omit the `admin_read` branch; `ensureDatabasePermission` also omits the node-manage branch. `ensureBackupAccess` gets this right by using `hasGrant` (backups.ts:80-83). One canonical path (`ensureServerAccess`) should decide all of them.
- **V1 — propose `file.sftp` (new, targeted, subuser-grantable):** capability "mint/rotate SFTP access tokens for this server". Endpoints: GET /api/sftp/connection-info, POST /api/sftp/rotate-token (plus listing/revocation could stay owner/`server.update`). Today the mint gate is `server.read` (server.ts:1564, 1672) — a bare view-servers role can mint on every server — precisely because no targeted permission exists. `lib/validation.ts:227` already mentions `file.sftp` as a *syntax example only*; it is **not** in PERMISSION_CATEGORIES (permissions-catalog.ts:122-129 lists only `file.read`/`file.write`) and is enforced nowhere → D-CATALOG phantom. Either register it and use it, or delete the comment to stop implying it exists.
- **V2 — SFTP effective-permission derivation must match the panel contract.** The validate-token endpoint should return `getEffectiveServerPermissions(userId, server)` (owner → full set; `admin.read` → read subset containing `file.read`; node-manage → full set) instead of the current `isAdmin ? ["*"] : serverAccess?.permissions ?? []` (server.ts:1483-1488). Today owners get deny-all (functional bug) and `admin.read` cannot read files over SFTP even though it can over HTTP — an A-READ-GAP on a read stream.
- **V3 — keep `file.decompress`/compress/chmod/rename/delete under `file.write`; do not split.** Extraction writes arbitrary files (zip-slip class), chmod is privilege-relevant (agent clamps mode, file_manager.rs:1135-1157), rename is exfiltration-capable. `file.write` is the correct targeted gate. `archive-contents` correctly sits under `file.read` (files.ts:464) — read-classified, `admin.read` reaches it. No change needed; recorded so the vocabulary decision is explicit.
- **V4 — `backup.download` is well-formed:** registered in the catalog (permissions-catalog.ts:118), read-classified (permissions.ts:134), separately checked (backups.ts:539) so `backup.read` cannot stream archives. Keep as-is.
- **V5 — propose `database.host.read` (new, panel-level, NOT server-scoped):** capability "list panel database hosts". Replaces the GET /database-hosts "owns any server" fallback (databases.ts:24-32), which currently exposes infra hostnames/ports to any subuser of any server. `admin.read`/`admin.write` imply it via hasGrant. Do not add to ALL_SERVER_PERMISSIONS (it is not per-server).
- **V6 — `node.update` + node assignment grants full server writes (E-BROAD, by design).** decideServerAccess's `node_manage` reason (server-access.ts:64-66) yields `file.write`/`backup.restore`/etc. on every server on the assigned node — broader than any file/backup permission, with no per-operation narrowing. This is the documented single-source contract (_helpers.ts:1298-1304), so treat as a design decision: either document it in the permission catalog UI or narrow node managers to a defined subset. Flagging per the "narrowly scoped" target; no per-row verdict change.
- **V7 — dead/stale artifacts found while auditing (non-permission):** stale "up to 1 year" comment at server.ts:1449 (actual max 24h, sftp-token-manager.ts:68); copy-paste comment files.ts:147; dead comment databases.ts:468; `listSftpTokensForServer`'s unused `isOwner` parameter (sftp-token-manager.ts:335) making the route comment "owner-only, or self-view" (server.ts:1706) false.

## 4. Fix List (priority order)

1. **F1 — backups.ts: enforce API-key scope (B-WRITE-LEAK, K1).** Add an `actor` parameter to `ensureBackupAccess` (backups.ts:43-96), pass `request.user` at all six call sites (106, 175, 263, 306, 465, 539), and call `enforceKeyScope(actor, permission)` on every allowed branch — or simply replace the helper with `ensureServerAccess` (it already implements owner/ServerAccess/role/node-manage + key-scope identically, _helpers.ts:495-558).
2. **F2 — server.ts:1483-1488: fix SFTP session permission derivation (A-READ-GAP + owner bug).** Replace `isAdmin ? ["*"] : serverAccess?.permissions ?? []` with the result of `getEffectiveServerPermissions(result.userId, server)` (owner/node-manage → full set; `admin.read` → read subset; else ServerAccess ∪ role grants). This restores owner SFTP and gives `admin.read` SFTP read.
3. **F3 — databases.ts:48-55 / _helpers.ts:1446-1515: close the database list read gap.** Use `ensureServerAccess(serverId, userId, "database.read", reply, request.user)` for GET /:serverId/databases (and reuse it in create/rotate/delete to retire `ensureDatabasePermission` or make it delegate to `decideServerAccess`). Restores `admin.read` reads and node-manage consistency; key-scope already enforced there.
4. **F4 — server.ts:1559-1565 and 1667-1673: narrow the SFTP mint gate and enforce key scope.** Change `requiredPermission: "server.read"` → `"file.read"` (or the new `file.sftp`), keep the ServerAccess row filter (already requires server.read/file.read/file.write, server.ts:1543-1547), and add `enforceKeyScope(request.user, perm)` so a narrow API key cannot mint a `["*"]`-validating token.
5. **F5 — server.ts:1744-1749: pass `requiredPermission` (e.g. `"file.read"`) to the GET /api/sftp/tokens decision** so the `admin_read` branch is reachable; while there, honor `canManageTokens` (F8).
6. **F6 — databases.ts:10-39: gate GET /database-hosts on a permission** (`admin.read` or new `database.host.read`), and stop listing all hosts to users whose only qualification is owning one server; scope host visibility to hosts referenced by the caller's accessible servers.
7. **F7 — lib/validation.ts:227 + permissions-catalog.ts:122-129: resolve the `file.sftp` phantom** — register `file.sftp` (and wire it per F4) or remove the comment. Also decide V6 (document/narrow node_manage full-write).
8. **F8 — services/sftp-token-manager.ts:332-368: make `listSftpTokensForServer` honor its `isOwner`/manager parameter** (currently unused), so non-managers see only their own token entries; fixes the metadata exposure noted on GET /api/sftp/tokens.
