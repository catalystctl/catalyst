# Permission Audit — Agent-Side (Rust) Authorization Surface

Scope: `catalyst-agent/src/websocket_handler/mod.rs` (control-plane handshake + op dispatch), `catalyst-agent/src/sftp_server.rs`, `catalyst-agent/src/file_manager.rs` (path jail), `catalyst-agent/src/file_tunnel.rs`, with panel-side counterparts cited for context (`catalyst-backend/src/websocket/gateway.ts`, `routes/file-tunnel.ts`, `server.ts`, `services/sftp-token-manager.ts`). Companion to `audit/permission-audit/server-files.md` (SF) and `plugins.md`. All claims cite file:line.

## 1. Executive Summary

The agent has exactly two trust anchors: the **node api_key** and, for SFTP only, the **panel-attested permission list**. The control-plane WebSocket uses a real challenge-response handshake (agent nonce, panel echo with a keyed tag) plus replay/timestamp/in-flight guards — after that, **every one of the 48 op types is authorized purely by connection possession**: no user identity or permission travels with any panel message, so the panel is trusted wholesale for file ops, power ops, console input, backups, and even agent self-update/config-rewrite. The file-tunnel channel (used by the panel's `/api/servers/:id/files/*` routes) is the same model over HTTP: node-key-authenticated, requests carry only (operation, serverUuid, path) — the panel's route-level authz is the only authorization layer. SFTP is the one surface with real per-request authorization: the agent checks `file.read`/`file.write`/`*` **per operation** against the permission list the panel returned at token validation, inside a robust canonical-path jail. Two facts dominate the SFTP fix design: (a) the agent performs **no permission inference** — a list of `['admin.read']` is deny-all, so the panel must map effective server perms into the agent's exact vocabulary; and (b) permissions are a **session-open snapshot with no mid-session revalidation** — panel-side revocation never reaches a live SFTP session (`revalidateSftpSession` is dead code), so a stale permission list is enforced until the client disconnects.

## 2. Surface 1 — Control-plane WebSocket handshake (websocket_handler/mod.rs)

**What is enforced, where:**
- Agent generates a 128-bit random nonce and sends it in `node_handshake` together with the api_key token (mod.rs:1542-1557). The panel must reply `node_handshake_response` echoing the nonce plus `authTag` = SHA-256(api_key ‖ nonce ‖ node_id) hex (mod.rs:149-159), compared in constant time (mod.rs:161-171, 186). Verified at mod.rs:3242-3267; failure → `SecurityViolation` → reconnect (3255-3261).
- **Gate**: until verification succeeds, every inbound frame is dropped except `node_handshake_response` and `error` (mod.rs:1933-1947). Only the panel that knows the api_key can ever get an op processed.
- **Replay protection**: every frame carrying a `requestId` is deduped through a bounded LRU (5k entries, mod.rs:124, 189-217) keyed on (requestId, type) — multi-step streaming flows reuse one id deliberately (mod.rs:1916-1926) — and a ±5-minute timestamp window rejects skewed frames (mod.rs:125-126, 219-223, 1903-1915). Missing timestamps are allowed for legacy panel frames (comment at 219-220).
- **DoS guards**: 32 in-flight commands max with busy-response (mod.rs:135-136, 1949-1967), per-server mutex across validate→mutate→exec (mod.rs:3336-3338, 2378-2386), 4 MB frame / 8 MB message caps (mod.rs:1517-1519), panel-supplied retryAfter clamped to 300 s with consecutive-lockout cap so a hostile panel cannot park the agent forever (mod.rs:127-130, 227-243, 3271-3292).

**What it trusts:** once the handshake passes, the *connection* is the panel. The dispatch (mod.rs:1969-3271) accepts 48 op types — power (`server_control` install/start/stop/kill/restart at 1970, 3322-3439; dedicated `start/stop/kill/restart_server` at 2080-2190), install/reinstall/rebuild/delete (1971-2323), `console_input` (2355-2361), `file_operation` (2362-2372), full backup lifecycle incl. restore and streaming download (2373-2533), clone/resize (2553-2591), network management (2893-3237), and **agent self-management**: `update_agent` (2623), `restart_agent` (2894), `agent_config_update` — which rewrites the agent's own TOML, with an `allowUnsafe` variant that backs up first (3092-3233) — and `agent_logs` (2933). None of these messages carry a user id or permission; there is nothing to check. Authorization = possession of the api_key, full stop. The only defense-in-depth on top: `server_control` refuses a `suspended: true` flag **relayed by the panel in the message body** (mod.rs:3327-3331) — panel data, agent-enforced.

**Notes:** (1) The tag is a plain SHA-256 over secret-first concatenated input, not literal HMAC as comments say (mod.rs:140-142) — with a high-entropy api_key this is still a sound MAC (single hash, no length-extension exposure), but worth knowing. (2) The api_key itself travels in the handshake message (mod.rs:1547-1557) and channel confidentiality depends on the `wss://` scheme being used in production configs. (3) Panel-side counterpart: gateway verifies the agent token via `verifyAgentApiKey` and computes the same tag for the echo (gateway.ts:1738-1748) — mutual authentication in effect.

## 3. Surface 2 — SFTP server (sftp_server.rs)

**What is enforced, where:**
- **Auth method**: password only; publickey rejected both at offer and at signature (sftp_server.rs:1189-1207). Username = serverId, password must be `sftp_`-prefixed (1209-1218).
- **Token validation**: the agent POSTs to the panel's `/api/agent/sftp/validate-token` with `X-Node-Id` + `X-Node-Api-Key` headers (sftp_server.rs:259-318) — i.e. the *panel* authenticates itself to the agent on this call. The panel returns `{userId, serverUuid, permissions}` (response parsing 297-317).
- **Jail binding**: the session's file root is the **panel-returned `serverUuid`** (set at 1229-1231, handler constructed with it at 1297-1303), never the client-typed username. The client's username is only used inside the validate call, where the panel checks token↔server binding and cross-node replay (server.ts:1420-1463, audited in SF).
- **Per-op permission enforcement** — `has_permission` = list contains `*` OR the exact string (sftp_server.rs:399-400): `open` splits read/write by open flags (480-491); `read` (578-580, with an explicit comment that handles are forgeable strings); `write` (640-642); `lstat`/`fstat` (730, 759); `setstat`(chmod)/`fsetstat` (788, 811); `opendir`/`readdir` (831, 877, ditto forgeable-handle comment); `realpath`/`stat` (1017, 1060); `remove`/`mkdir`/`rmdir`/`rename` (955, 976, 996, 1091). `symlink`/`readlink`/`extended` are not implemented (1109-1130). **Every op re-checks; nothing is trusted from the session-open handshake.**
- **Path safety (independent of permissions)**: all paths resolve through `FileManager::resolve_path` with a canonical-base jail (file_manager.rs:564-668: canonicalize server base, join, re-canonicalize, reject escape, parent-canonicalize fallback for not-yet-existing targets), ancestor-symlink revalidation closing the `create_dir_all` window (file_manager.rs:82-128), `O_NOFOLLOW` opens for read/write/target-probe (file_manager.rs:49-62; sftp_server.rs:504-510, 588-594, 664-691), chmod clamped to safe modes (file_manager.rs:1135-1157), and the jail rejects traversal-style server ids outright (file_manager.rs:64-80; test at 2065).
- **Mutation notifications**: SFTP mutations emit `server_files_changed` events to the panel (sftp_server.rs:125-195) so the panel UI stays consistent with out-of-band writes.

**What it trusts:** the panel's validate-token response verbatim — `permissions` is enforced as-is, with no expansion or inference. `['admin.read']`, `['server.read']`, or `[]` all mean deny-all on the agent; only `file.read`, `file.write`, and `*` have meaning. The `serverUuid` is trusted as the jail root (the panel is the authority on which server the token belongs to).

**Critical finding — snapshot semantics:** permissions are captured once at password auth (sftp_server.rs:1220-1232) and frozen into the handler for the session's lifetime (1303). **No agent-side revalidation exists**: token expiry (panel TTL cap 24 h, sftp-token-manager.ts:62-68) blocks only *new* connections, and panel-side revocation (`revokeSftpToken` → backend cache-bus 'sftp' flush, sftp-token-manager.ts:15-28) never reaches the agent. The panel's `revalidateSftpSession` (sftp-token-manager.ts:186-214) — whose docstring says "Agents call this on session heartbeat; a false return must kill the session" (184-185) — is called from a *test only* (sec-m-hardening.test.ts:136): a documented contract with no implementation on either side. A revoked or permission-shrunk user keeps full session powers until they disconnect.

## 4. Surface 3 — File-tunnel (the panel's file-routes channel)

**What is enforced, where:** the agent long-polls `/api/internal/file-tunnel/poll` authenticating itself with `X-Node-Id` + `X-Node-Api-Key` (file_tunnel.rs:181-196; panel side verifies via `verifyAgentApiKey`, routes/file-tunnel.ts:25-50). Each queued request carries only `(requestId, operation, serverUuid, path, data)` and is dispatched to a handler with **no permission checks of any kind** (file_tunnel.rs:254-300): list/download/upload/write/create/delete/rename/permissions/compress/decompress/archive-contents/install-url all execute directly against the FileManager jail. Upload fetch and response submission use the same node-key headers (file_tunnel.rs:342-351); the panel binds responses and uploads to the authenticated node (services/file-tunnel.ts:268, 291 — verified in SF §2.2).

**What it trusts:** the panel completely. This is the answer to "does the panel send user identity/permissions with file ops?": **no** — the request contains no user id and no permission list; the panel's route-level authz (`ensureServerAccess` with `file.read`/`file.write`, files.ts:115/206/etc.) is the *only* authorization layer standing between a panel user and the agent's filesystem. Node-key possession = unrestricted read/write of every server's files on that node. This is a coherent design (the panel is the policy decision point, the agent the enforcement point for paths only), but it means the panel's permission bugs translate 1:1 into agent-side file access, with no agent-side backstop.

All of these share the Surface-1 trust model: connection possession = authorization. The clamps (retryAfter, upload ceiling, log lines) are the only protections against a *compromised* panel, and they are explicitly operator-scoped (SEC-H-03/H-04 comments, mod.rs:127-134).

## 6. SFTP fix design constraints — the contract the panel must uphold

These are the hard requirements any panel-side SFTP fix (SF F2/F4/F5) must satisfy to work correctly against this agent:

1. **Vocabulary is closed and exact.** The agent matches only the literal strings `file.read`, `file.write`, and `*` (sftp_server.rs:399-400). There is no read/write inference, no `admin.read`/`admin.write` handling, no `server.read` fallback. A validate-token response returning `['admin.read']` or `['server.read']` produces a **deny-all** session.
2. **The validate-token response must be the caller's EFFECTIVE server permission set, mapped into that vocabulary.** The current derivation (server.ts:1483-1488: `isAdmin(* /admin.write) ? ["*"] : serverAccess?.permissions ?? []`) is what breaks owners (no ServerAccess row → `[]`) and read-admins. The fix must reuse `getEffectiveServerPermissions(userId, server)` (_helpers.ts:1374-1435), which already implements the right mapping: owner / node-manage / `admin.write` / `*` → full set (contains `file.read` + `file.write`), `admin.read` → read subset (contains `file.read`), subuser → ServerAccess ∪ role-granted server permissions. The agent will then enforce exactly that granularity per op.
3. **Mint gate and validate derivation are independent — fix both, in this order of importance.** The mint check (SF F4: `server.read` → `file.read`) only decides who can *obtain* a token; the validate response decides what the session can *do*. Because the agent enforces the validate list per op, a token minted by an under-privileged caller is safe-by-construction **as long as** the validate derivation is correct — the mint gate then only stops toothless tokens and node host/port disclosure. Conversely, fixing only the mint gate (requiring `file.read`) while leaving the derivation would *still* give `["*"]` sessions to keys of admin users.
4. **Revocation does not propagate.** Panel-side `revokeSftpToken`/TTL expiry never reach a live session (no agent revalidation; `revalidateSftpSession` is dead code — sftp-token-manager.ts:184-214 called only from sec-m-hardening.test.ts:136). If the fix claims "revoke takes effect immediately," it must add one of: (a) an agent-side per-session heartbeat calling a panel revalidation endpoint that kills the session on `false` — the contract the docstring already promises; (b) a panel→agent push over the control-plane WS (the `dispatch_outbound_event` plumbing exists, mod.rs:69-99, and the SFTP server already holds an outbound channel); or (c) an explicit agent-side session max-age, since the 24 h TTL bounds only token minting, not session lifetime. Without one of these, grants shrunk on the panel keep full force on existing sessions.
5. **Keep returning `serverUuid` and keep the node-binding check.** The agent keys the file jail on the panel-attested UUID, not the client username (sftp_server.rs:1229-1231, 1297-1303), and the cross-node check (server.ts:1457-1463) is what stops node B validating node A's tokens. Any refactor of validate-token must preserve both.
6. **Keep the `sftp_` token prefix and format.** The agent rejects non-`sftp_` passwords outright (sftp_server.rs:1212-1218); the panel mints `sftp_<64 hex>` (sftp-token-manager.ts:119). Key-scope enforcement (SF K1) must happen at mint/rotate time on the panel — the agent has no concept of API keys.
7. **Path safety is already the agent's job — don't duplicate it panel-side.** Jail, ancestor-symlink revalidation, `O_NOFOLLOW`, and chmod clamping are enforced regardless of the permission list (file_manager.rs:49-128, 564-668; sftp_server.rs:504-510, 588-594, 664-691). The panel fix only needs to get the permission list right.
