# API Permission Audit — Alerts Domain (routes/alerts.ts)

Auditor: `audit-infra` · File: `catalyst-backend/src/routes/alerts.ts` (700 lines, 11 endpoints, registered under `/api` at server.ts:1100 → `/api/alert-rules` and `/api/alerts`). Companion audits: `infra.md` (nodes/locations/nests/templates), `test-plan.md`.

## Executive summary

- 11 endpoints audited. Verdicts: **OK 4 · D-CATALOG 2 · B-WRITE-LEAK 5 · A-READ-GAP 0 · C-NO-CHECK 0 · E-BROAD 0**. All 11 `isAdminUser` call sites pass the correct mode (admin.write for the 5 writes, admin.read default for the 6 reads — see table) — no nodes.ts-style mode bugs.
- **Systemic key-scope bypass (the tracked P0, fully manifested here):** no endpoint threads `request.user` (no `apiKeyId` check, no `enforceKeyScope`, no actor parameter). Every authorization decision re-resolves the **user's live role permissions** via `getUserPermissions(prisma, userId)` (alerts.ts:12-23, :61-62), ignoring the API key's declared scope entirely. A key scoped to `['server.read']` belonging to an admin.write user exercises full admin power on all 11 routes (create/delete global rules, resolve anyone's alerts, read all deliveries). The 5 write rows are B-WRITE-LEAK; the 6 read rows carry the same hole (tagged K-SKIP).
- **`alert.read` is semantically dead** (D-CATALOG): `GET /alerts` hard-filters `where.userId = user.userId` for every non-admin (alerts.ts:446-448), and `GET /alerts/:id` / `/deliveries` 403 non-owners at :515/:372 *before* the `alert.read` server-check at :518/:375 can apply. A role or preset holding `alert.read` ("View alerts") can never see anyone else's alerts — it only lets the rule creator read their own alerts on servers they don't own. The existing regression test pins only "non-403" (alerts-access-rbac.test.ts:148-155), masking the empty result set.
- `alert.create/update/delete` are alive and correctly scoped: they gate non-admin server-targeted rule mutations and resolve via ServerAccess rows, global-role grants, or node_manage (alerts.ts:148-154, :279-290, :337-348, :553-563, :621-632). Global/node rule targets are admin-only (alerts.ts:168-170, :276-278, :334-336) — correctly narrower than server targets.
- **Webhook secrets echo verbatim:** `AlertRule.actions.webhooks` URLs (schema.prisma:957; Discord/Slack tokens live in the URL path) and `AlertDelivery.target` (the same URLs / email addresses, alert-service.ts:648-677) are returned unredacted by rule reads and delivery reads. Gated owner-or-admin so no cross-user leak today — but any fix that grants `alert.read` real visibility (P1) will expose them unless redaction ships with it.
- Ownership quirk: `Alert.userId` = **rule creator** (alert-service.ts:206, :234, :260, :297, :322, :347, :410, :455), not the affected server owner — server owners cannot see alerts fired on their own servers by someone else's rule (non-admin, non-owner → 403 at :515 / empty list at :447).

## Vocabulary findings

1. **`alert.read` — dead capability (D-CATALOG, rows 7-8).** In catalog (permissions-catalog.ts:151-160 "View alerts"), granted by the support/moderator presets (permissions.ts:574, :598), enforced in this file only as an access *gate* (ensureServerAccess requiredPermissions at :381, :427, :524). The result-set filters (`where.userId`, alerts.ts:446-448; owner-403 ordering :515, :372) make it impossible for a non-admin non-owner to ever see an alert. Net effect of holding `alert.read`: a rule creator may read their *own* alerts on servers they don't own — nothing resembling "View alerts". Either grant real server-scoped visibility (recommended — matches the comment's stated intent at alerts.ts:58-60) or remove it from presets until it does something.
2. **`alert.create` / `alert.update` / `alert.delete` — live and well-scoped.** They gate non-admin server-targeted rule mutations (create :153, update :285, delete :343) and alert resolution (:559, :627) via three equivalent paths: ServerAccess row `hasSome` (:48-54), global/RoleServerGrant/RoleNodeGrant role perms (:61-65), node_manage (:68-73). Global/node rule targets correctly require admin bits (:168-170, :276-278, :334-336). No vocabulary change needed for these three.
3. **No missing catalog strings:** every permission enforced here (`admin.read`, `admin.write`, `alert.create/update/delete/read`, `node.update`) exists in PERMISSION_CATEGORIES. The gap is enforcement semantics, not vocabulary.
4. **Scoped permission strings are dead here (parity with nodes.ts):** `rolePerms.includes(permission)` (alerts.ts:63) is a raw exact-match — a role granting `alert.read:serverX` (scoped form honored by `permissionMatches` elsewhere) grants nothing in this file. Low priority (RoleServerGrant rows are the intended per-server mechanism and do work), but any consolidation should switch :63 to `hasGrant`-style matching.
5. **`Alert.userId` semantics = rule creator, not server owner** (alert-service.ts:206 et al.). Consequences: (a) server owners can't see alerts fired on their own servers from others' rules; (b) alert.create via ServerAccess lets a subuser create a rule whose alerts are visible only to themselves — not to the server owner. Document or change the ownership model for server-scoped alerts (product decision; affects the fix-#2 visibility design).
6. **Webhook secrets in readable payloads:** `AlertRule.actions` (JSON — webhook URLs with embedded tokens, emails; schema.prisma:957) and `AlertDelivery.target` (alert-service.ts:652, :667, :677, :760) are returned verbatim by rows 2, 3, 6, 7, 8. Gated owner-or-admin so no cross-user exposure today; but fix #2 (alert.read visibility) MUST ship with redaction or it becomes a leak. SSRF is already guarded at dispatch time (alert-service.ts:661-673, pinned by security-fixes-regression.test.ts:11-75) — the route itself accepts arbitrary URLs at write time (no URL validation in alerts.ts), which is acceptable given the dispatch guard.
7. **Key-scope vocabulary:** the file needs the same actor-threading contract as servers/_helpers.ts:487-493 (`enforceKeyScope`) and admin.ts:1591-1598 (inline ceiling). The cleanest form here: since the middleware already guarantees `request.user.permissions ⊆ user role perms` for scoped keys (server.ts:494-508) and equals role perms for sessions/allPermissions keys, the local `isAdminUser` should consume `request.user.permissions` via `hasGrant(perms, 'admin.read'|'admin.write')` (the admin.ts:73-76 `checkPerm` pattern) instead of re-resolving roles from the DB.

## Fix list (priority order)

**P0 — key-scope bypass (all 11 rows)**
1. alerts.ts:12-23 — replace the DB-resolution `isAdminUser` with the request-scoped pattern: `const isAdmin = hasGrant(request.user?.permissions ?? [], 'admin.write')` (mode per call site, exactly as today). Sessions and allPermissions keys are unaffected (middleware sets their perms to the live role set); scoped keys become correctly ceiling-limited. Mirror across :84, :209, :235, :259, :324, :366, :420, :493, :541, :602, :675. (Alternative: keep DB resolution for the admin flag but add `enforceKeyScope(request.user, 'alert.*'|'admin.write')` per route — the single-switch above is smaller and matches admin.ts.)

**P1 — alert.read visibility (rows 7-8)**
2. alerts.ts:446-448 — when the caller holds `alert.read` via role or ServerAccess for the queried server(s), return alerts scoped to those servers instead of `where.userId`; alerts.ts:515-517 — admit ServerAccess/role `alert.read` holders for alerts on their servers (reorder so the server-scope check at :518-529 is the authority, not the owner match); same for :372 (deliveries). Ship together with fix #4 (redaction) — see vocabulary finding 6.

**P2 — sensitive-payload redaction**
3. Mask webhook URLs and emails in API responses: `AlertRule.actions` on rows 2-3 (and POST/PUT echo bodies :187, :304) and `AlertDelivery.target` on rows 6-8. Keep full values for `admin.write`/`*` or the rule owner only; redact token path segments (e.g. keep scheme+host) for everyone else.

**P3 — semantics / hygiene**
4. alerts.ts:63 — `rolePerms.includes(permission)` → `hasGrant(rolePerms, permission)` so scoped grants and admin bits behave consistently inside ensureServerAccess.
5. Document or change `Alert.userId` ownership for server-scoped alerts (vocabulary finding 5) — at minimum, note it in the fix-#2 design so visibility rules are deliberate.
6. Document the `scope=mine|all` default on rows 2, 7, 11 (admins default to `mine`; `?scope=all` is the panel-wide view) — or flip the admin default to `all` for parity with admin.read = read-everything. Either way, add it to the contract matrix expectations (test-plan.md §3.6).
