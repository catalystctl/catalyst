# Internationalization (i18n)

Catalyst ships with i18n support for the panel UI. English (`en`) is the source
language; every other locale is a translation of it. Untranslated keys fall back
to English at runtime, so a partial translation never breaks the interface.

Currently supported locales:

| Code | Language | Status |
|------|----------|--------|
| `en` | English | Source language |
| `zh-CN` | Chinese (Simplified) | In progress — app shell, navigation, dashboard, shared labels and error messages translated; remaining namespaces fall back to English and are open for contribution |

## How it works

- **Library**: [i18next](https://www.i18next.com/) + [react-i18next](https://react.i18next.com/).
- **Catalogs**: JSON files in `catalyst-frontend/src/i18n/locales/<locale>/<namespace>.json`.
  They are bundled into the application build (no runtime fetch), so translations
  work offline and are covered by the service worker's asset cache.
- **Loading**: the `common` and `errors` namespaces are bundled for instant first
  paint. Every other namespace is a separate chunk loaded on demand by a small
  i18next backend that reads the catalogs through `import.meta.glob`.
- **Fallback**: `en` is the fallback language. A key that is missing — or present
  with an empty string value — resolves to the English text.
- **Language detection order**: an explicit device choice (localStorage key
  `catalyst-language`) → the signed-in user's saved preference
  (`User.preferences.locale`) → the browser's `navigator.languages` → English.
- **Persistence**: changing the language in the UI stores it for the device and,
  when signed in, saves it to the user's preferences so it follows them to other
  browsers. Signing out restores the device language.
- **`<html lang>`** is updated whenever the language changes.

## Namespaces

Each namespace maps to an area of the application:

| Namespace | Area |
|---|---|
| `common` | Shared UI components, generic actions, statuses |
| `errors` | Backend error codes and generic error text |
| `validation` | Client-side validation messages |
| `layout` | App shell, sidebar, header, search palette |
| `auth` | Sign-in, registration, password reset, invites |
| `setup` | First-run setup wizard |
| `dashboard` | Dashboard page |
| `servers` | Server list and server detail shell |
| `server-tabs` | Server tabs: console, files, backups, tasks, startup, schedules, databases, network, subusers |
| `nodes` | Node pages |
| `templates` | Template pages |
| `alerts` | Alerts and notification settings |
| `profile` | Profile, sessions, API keys, appearance |
| `plugins` | Plugin host and plugin surfaces |
| `admin` | Admin dashboard and shared admin widgets |
| `admin-infra` | Admin nodes, servers, allocations, databases, migrations |
| `admin-access` | Admin users, roles, audit log, security |
| `admin-system` | System settings, system errors, theme, plugins |

A namespace is loaded when a component calls `useTranslation('<namespace>')`, so
adding keys only affects users who visit that area.

## Key conventions

- Keys are nested and semantic: `auth.login.title`, `servers.actions.start`.
- Interpolation uses `{{name}}`: `"deleteConfirm": "Delete {{name}}?"`.
- Plurals use i18next suffixes (`_one`, `_other`):

  ```json
  {
    "session_one": "{{count}} session",
    "session_other": "{{count}} sessions"
  }
  ```

  Call them as `t('session', { count })`. Chinese has a single plural form and
  only needs `_other`.
- Never build keys dynamically (`t('status.' + status)`). Add an explicit
  value-to-key map instead. The only dynamic lookups are backend error codes in
  the `errors` namespace and validation rule codes in `validation`, which the
  tooling preserves automatically.
- Dates, numbers and relative times go through `src/i18n/format.ts` rather than
  `toLocaleString()` with a hardcoded locale.

### Shared vocabulary

Generic labels live in `common` and are reused across areas instead of being
re-translated per screen:

- `actions.*` — save, cancel, delete, edit, close, retry, refresh, …
- `status.*` — server states, rendered through `serverStatusLabel(t, status)`
  in `src/utils/constants.ts` (a switch over literal keys, so extraction and
  translation stay exact).
- `statusBadge.title` — the tooltip on the server status badge.

Use these rather than adding a second spelling of the same button label in a
feature namespace.

## Writing translatable code

```tsx
import { useTranslation } from 'react-i18next';

function StartButton({ name }: { name: string }) {
  const { t } = useTranslation('servers');
  return <button>{t('actions.startServer', { name })}</button>;
}
```

- **Components** use `useTranslation('<namespace>')`; the namespace is loaded on
  demand.
- **Non-React modules** (formatters, stores, helpers) use the shared instance:
  `import i18n from '@/i18n';` then `i18n.t('key', { ns: 'servers' })`.
- **Interpolation** uses `{{name}}`; **plurals** use `t('key', { count })` with
  `_one`/`_other` variants in the catalog.
- **Dates, numbers and relative times** go through `src/i18n/format.ts`
  (`formatDate`, `formatDateTime`, `formatNumber`, `formatRelativeTime`) instead
  of `toLocaleString()` with a hardcoded locale.
- **API errors**: pass the thrown error to `notifyError(error)` (or use
  `getLocalizedErrorMessage(error)`); known backend codes resolve to translated
  text, unknown ones keep the server's English message.
- **Validation messages**: prefer stable schema codes over raw text; the
  `validation` namespace translates `VALIDATION_TOO_SMALL`,
  `VALIDATION_INVALID_FORMAT`, … with `{{min}}`/`{{max}}` interpolation.
- **Don't translate**: identifiers, CSS classes, URLs, version strings, log and
  debug messages, `SystemError` diagnostics, product names (Catalyst), and the
  Rust agent's output.

After changing code, run `pnpm i18n:extract` from the repository root: it adds
new keys to the English catalogs and placeholder entries to other locales
(empty string values fall back to English at runtime). `pnpm i18n:verify` fails
if a catalog is out of date, and `pnpm --filter catalyst-frontend run i18n:lint`
flags hardcoded strings that were missed.

## Backend error codes

Every API error response carries a stable code:

```json
{ "error": "Server is already running", "code": "SERVER_ALREADY_RUNNING" }
```

- Codes live in `catalyst-backend/src/lib/error-codes/<domain>.ts` and are
  merged into `ErrorCodes`; add new ones to the matching domain file.
- Route handlers send errors through `apiError(reply, status, code, message,
  { params, details })` (`catalyst-backend/src/lib/http-error.ts`). `message`
  stays English and is the fallback for clients without a translation.
- Validation failures include field-level details with rule codes
  (`formatZodIssues` in `catalyst-backend/src/lib/validation.ts`).
- To translate a new code, add it to `errors` in
  `catalyst-frontend/src/i18n/locales/en/errors.json`; `pnpm i18n:check` warns
  about backend codes that have no entry.

## Contributing translations

1. Pick the locale directory you want to work on, for example
   `catalyst-frontend/src/i18n/locales/zh-CN/`. If the file for a namespace does
   not exist yet, copy the English one and translate the values.
2. Translate values only — never change keys, and never change `{{placeholders}}`.
3. Check your progress:

   ```bash
   pnpm i18n:status            # summary of every locale
   pnpm i18n:status zh-CN      # per-key report for one locale
   pnpm i18n:check             # validates JSON and reports catalog problems
   ```

4. Run the panel with your language selected (profile → Appearance → Language,
   or the globe menu on the sign-in screen) to review your work in context.
5. Open a pull request. Partial translations are welcome; English fallback keeps
   the UI complete until the remaining keys are translated.

### Adding a new locale

1. Add an entry to `SUPPORTED_LOCALES` in `catalyst-frontend/src/i18n/config.ts`
   (`code`, `englishName`, `nativeName`) and add the code to `locales` in
   `catalyst-frontend/i18next.config.ts`.
2. Create `src/i18n/locales/<code>/common.json` and `errors.json` (required,
   because they are bundled) and translate them.
3. Add the remaining namespace files as they are translated; missing files and
   keys fall back to English.
4. If the language is written right-to-left, note it in the pull request — RTL
   layout support is tracked separately and the CSS may need follow-up work.

### Translating backend error codes

API errors carry a stable code (for example `SERVER_NOT_FOUND`). These codes are
translated in the `errors` namespace, keyed by the code itself:

```json
{
  "SERVER_NOT_FOUND": "找不到请求的服务器。"
}
```

`pnpm i18n:check` warns when a backend code has no English entry, so new backend
codes are added to `en/errors.json` first and translated afterwards.

## Tooling

All commands run from the repository root:

```bash
pnpm i18n:extract          # extract keys from source into the en catalogs
pnpm i18n:status           # translation completion report
pnpm i18n:check            # catalog validation (CI runs this)
pnpm --filter catalyst-frontend run i18n:lint   # find hardcoded strings
```

`i18next-cli` performs the extraction. Keys inside `t()` / `useTranslation()`
calls are detected automatically; the `errors` and `validation` namespaces are
excluded from unused-key pruning because they are looked up dynamically.

## Scope

Localized today: the entire panel UI, backend error codes (translated
client-side), and emails/alerts rendered for the recipient's language.

Deliberately not localized: the Rust node agent's log and error strings,
administrator-facing `SystemError` entries (diagnostics stay in their original
wording for searchability), third-party plugin UI that ships its own strings,
and documentation prose. Translating the documentation is tracked separately in
[CONTRIBUTING.md](../CONTRIBUTING.md).
